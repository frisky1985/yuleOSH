1. 目标与结论

本轮工作的目标是把 ASPICE 所需的过程证据从「散落在 pipeline 里的隐式产物」, 收敛为「桌面端可执行、可落盘、可审计的工作流」, 并让一个项目能够一键产出完整的审计交付物。

结论：P1–P9 全部完成并提交。支持过程域 SUP.1 / SUP.8 / SUP.9 / SUP.10 与管理过程域 MAN.3 已形成最小闭环；合规包、审计报告、可视化仪表盘均可由桌面 API 一键生成。 所有新增工作流均遵循 fail-closed（无证据即不通过），未引入「假绿」路径。
边界声明（必须保留）： E1–E3 仅为证据覆盖度分级，由通过状态证据的占比计算得出， 不是 Automotive SPICE 能力等级（Capability Level）， 也不构成任何正式 ASPICE 评估结论。正式评估须由经认可的评估机构执行。

4. 设计原则落实情况

4.1 反假绿（fail-closed）

场景预期行为验证
空项目 / 无需求审计状态 not_run、覆盖度 NI，不静默通过TestComplianceAudit
问题未验证即关闭返回 409 InvalidTransitionTestIssues
QA 审计仍有未结不符合项审计保持 open，不自动关闭TestQAWorkflow
风险无缓解措施即标记已缓解拒绝（400）TestProjectMgmt
BP 总数为 0环形图不渲染，避免伪造 0%TestAuditVisualization
未识别的合规检查项记 failed，无 fallback 通过compliance_checker 既有逻辑

4.2 证据可被合规检查消费

新增工作流的产物不是孤立文件：ComplianceChecker 已扩展为直接识别 .osh/issues/*.json、.osh/risks/*.json 与 .osh/project/milestones.json，对应 SUP.9 与 MAN.3 检查项由 「无证据 → RED」转为「有结构化证据 → 通过」。测试中通过 _has_issue_records() / _has_risk_records() / _has_milestone_records() 直接断言。

4.3 零外部依赖的可视化

仪表盘全部使用内联 SVG 生成（条形图、环形图、分布柱状图、gap 热力条形图）， 不引入 matplotlib / plotly / CDN，产物为单文件 HTML，可离线交付给审计方。

4.4 能力边界声明

P4 的 CAPABILITY_BOUNDARY 明确：CL1 supported、CL2 partial、CL3 不支持。 该声明与 E1–E3 免责声明贯穿 process-capability-map.md、审计报告与仪表盘， 避免把「证据覆盖度」误读为「能力等级」。

6. 已知限制与后续建议

限制 1：本轮覆盖的是「证据是否存在、状态流转是否合规」， 不对证据本身的技术正确性做判定（例如测试是否真的覆盖了需求语义）。
限制 2：SUP.1 / SUP.9 / MAN.3 为最小闭环， 未实现审批角色与权限体系；所有操作以 local 身份记录。
限制 3：E1–E3 的计算基于 passed-evidence 比例， 对证据数量敏感；证据稀疏的项目容易落在 NI，这是刻意保留的保守行为。

建议的下一步

  • 高为 QA / 风险 / 问题工作流补充角色字段与审批链，使 SUP.1 与 MAN.3 更接近完整过程。
  • 中把 P7–P9 的状态汇总接入 P6 仪表盘，形成「证据 + 流转」双视图。
  • 中在 compliance/run 中自动调用 QA/Issue/Milestone 导出，使合规包默认包含最新管理过程证据。
  • 低为桌面 API 增加 OpenAPI 描述，便于前端与外部工具对接。
