2. 后端契约对齐

接口返回信封前端处理
GET /projects/{id}/qa{ ok, audits[] } 取 res.audits ?? []，渲染摘要列表
GET /projects/{id}/qa/{audit_id}{ ok, audit } 批准前先拉详情，复核不符合项状态
POST /projects/{id}/qa/{audit_id}/approve{ ok, audit } 提交 { approver, role, note }；直接用返回值更新视图
错误（400）{ ok:false, error } apiFetch 抛出后端原文，组件原样展示
状态流转与后端一致：所有不符合项关闭后审计进入 pending_approval； 只有显式提交 approver 才转为 closed。空审计同样必须批准， 不因「没有不符合项」而自动通过。

3. 交互与防护设计

场景前端行为依据
列表中存在 open 审计 不显示「批准」按钮，仅可查看详情 未完成审计不可批准
批准人输入为空 「确认批准并关闭」禁用 后端要求 approver 非空
仍有不符合项未关闭 即使填写批准人，按钮仍禁用 fail-closed 双重校验
空审计（无不符合项） 显示「不代表质量合格」，仍需显式批准人 空审计 ≠ 合格
后端返回 400 展示后端错误原文，状态保持不变 错误如实反映，不吞异常
批准成功 就地更新详情并刷新列表 避免二次请求造成的状态漂移
