## 2. 工具功能分解

ISO 26262-8 §12 要求对工具的每个影响安全的功能进行独立评估。本章将 yuleOSH 分解为 **14 个功能模块**，每个模块按以下维度分析：

- **功能描述**: 该模块做什么
- **输入/输出**: 数据的来源和去向
- **安全相关性**: 该模块的输出是否可能影响 ASIL 产品的安全
- **故障模式**: 工具可能以哪些方式出错

### 2.1 F1 — OpenSpec 引擎

| 维度 | 描述 |
|:-----|:------|
| **功能** | 解析 RFC 2119 格式的需求规范 (SHALL/SHOULD/MAY + GIVEN/WHEN/THEN)，验证语法，生成需求树，追踪版本差异 |
| **输入** | 用户编写的 `spec.md` 文件 |
| **输出** | 结构化需求树 (SYS → SW → Feature → Scenario → Task)、需求 ID、状态机状态 |
| **安全相关性** | **高** — 需求解析错误可能导致安全需求被遗漏或误解，影响下游所有开发活动 |
| **故障模式** | 语法解析漏掉 SHALL 语句；需求树层次错误；需求 ID 冲突；状态机状态转换错误 |

### 2.2 F2 — AI Agent 流水线

| 维度 | 描述 |
|:-----|:------|
| **功能** | 10 步 LLM 编排流水线：spec → SDD → DDD → Code → Test → Review → C I，LLM 非强绑定 |
| **输入** | OpenSpec 规范、项目模板 |
| **输出** | 系统设计文档 (SDD)、详细设计文档 (DDD)、C/Python 源码、测试代码、审查记录 |
| **安全相关性** | **高** — AI 生成的代码可能包含安全缺陷；设计文档的错误导向下游所有实现 |
| **故障模式** | LLM 幻觉生成不安全代码；设计遗漏关键安全约束；测试代码不充分；阶段性输出不一致 |

### 2.3 F3 — 代码审查

| 维度 | 描述 |
|:-----|:------|
| **功能** | 4 Agent 并行审查矩阵：架构审查、领域审查、代码风格审查、测试覆盖率审查 + 资源预测 (stack/heap/flash/RAM) |
| **输入** | Git diff、源码、spec 引用 |
| **输出** | Review comment JSON 记录、审查报告 |
| **安全相关性** | **中** — 审查遗漏的缺陷可能进入下游，但审查记录完全可人工复核 |
| **故障模式** | AI 审查遗漏关键缺陷；审查建议误导性；资源预测偏差 |

### 2.4 F4 — MISRA 静态分析

| 维度 | 描述 |
|:-----|:------|
| **功能** | MISRA C:2023 规则自动检查，覆盖 ~120/169 条规则 |
| **输入** | C 源码 (.c/.h) |
| **输出** | MISRA 违规报告 (JSON/Markdown)、偏差记录 |
| **安全相关性** | **高** — MISRA 违规可能导致未定义行为和安全缺陷；漏报使违规代码悄声通过 |
| **故障模式** | 漏报 (~29% 规则不可检测)；误报 (20-30%)；复杂语义下漏检控制流/指针别名违规 |

### 2.5 F5 — CI L1 单元验证

| 维度 | 描述 |
|:-----|:------|
| **功能** | 运行 C (Unity) 和 Python (pytest) 单元测试；采集行/分支覆盖率；覆盖率门禁 |
| **输入** | 测试源码、编译后的测试二进制 |
| **输出** | 测试结果 JSON/JUnit XML、覆盖率报告 |
| **安全相关性** | **高** — 单元验证门禁是防止缺陷进入下一阶段的闸门；覆盖率为质量基线 |
| **故障模式** | 测试框架崩溃/超时导致误报失败；.gcda 文件损坏导致覆盖率数据丢失；测试自身缺陷 (假阳性) |

### 2.6 F6 — CI L2 集成验证

| 维度 | 描述 |
|:-----|:------|
| **功能** | 交叉编译 (ARM/RISC-V/x86-64)；SIL 仿真测试 (QEMU)；集成测试 |
| **输入** | 源码、编译脚本、QEMU 配置 |
| **输出** | SIL 测试报告、编译产物 (.elf/.bin) |
| **安全相关性** | **高** — 交叉编译产物直接用于硬件部署；SIL 仿真覆盖集成接口正确性 |
| **故障模式** | 交叉编译结果不一致 (ABI 差异)；QEMU 仿真不精确掩盖集成问题；MockHAL 模拟偏差 |

### 2.7 F7 — CI L2.5 HIL

| 维度 | 描述 |
|:-----|:------|
| **功能** | 硬件在环测试：固件刷写 → 串口监视 → 断言验证 |
| **输入** | 编译后固件 (.bin/.elf)、HIL 测试脚本 |
| **输出** | HIL 测试报告 |
| **安全相关性** | **中** — HIL 是真实硬件验证环节，故障可能导致硬件损坏或错误验证结果 |
| **故障模式** | 刷写失败误报为测试失败；固件完整性校验遗漏；硬件连接不稳定导致测试误判 |

### 2.8 F8 — 证据链引擎

| 维度 | 描述 |
|:-----|:------|
| **功能** | 收集所有 stage 输出，生成追溯矩阵，构建合规证据包，SHA-256 + RSA 签名 |
| **输入** | 所有 prior stage 输出 |
| **输出** | `audit-manifest.json`、合规 ZIP 包、追溯矩阵 |
| **安全相关性** | **低** — 证据包是信息聚合文档，不修改产品代码。但其完整性对审计至关重要 |
| **故障模式** | 证据文件遗漏；SHA-256 校验错误；跨引用解析失败；签名失败 |

### 2.9 F9 — 知识图谱 (TKG)

| 维度 | 描述 |
|:-----|:------|
| **功能** | 增量构建需求-代码-测试追溯图；影响分析查询；Merge Gate 验证 |
| **输入** | Spec、源码、测试、审查记录的解析数据 |
| **输出** | KG 数据库、度量报告、Merge Gate 判决 |
| **安全相关性** | **中** — KG 的 Merge Gate 影响代码合入决策；追溯矩阵用于审计证据 |
| **故障模式** | 增量构建漏建节点/边；合并门禁误判 (错误阻止/错误放行)；置信度计算偏差 |

### 2.10 F10 — 安全分析

| 维度 | 描述 |
|:-----|:------|
| **功能** | AI 辅助 HARA/DFA/FMEDA 分析，生成安全分析报告和 FMEA 条目 |
| **输入** | Safety Concept、HARA 表格、DFA 模型 |
| **输出** | 安全分析报告、FMEA 条目文件 |
| **安全相关性** | **高** — 安全分析输出直接影响安全设计决策 |
| **故障模式** | AI 遗漏关键故障模式；HARA 假设不足；FMEDA 数据错误；分析覆盖不全面 |

### 2.11 F11 — SaaS Dashboard

| 维度 | 描述 |
|:-----|:------|
| **功能** | Web 项目管理面板：流水线监控、项目管理、用户管理、订阅管理 |
| **输入** | 用户操作、API 请求 |
| **输出** | Web UI 呈现、项目管理状态变更 |
| **安全相关性** | **低** — Dashboard 是管理界面，不直接生成或修改产品代码。但错误配置可能影响工具行为 |
| **故障模式** | 权限配置错误；项目隔离失效；API 鉴权绕过 |

## 3. 工具影响评估 (TI)

### 3.1 TI 判定方法

根据 ISO 26262-8:2018 §12.4.3，TI 判定基于以下两个问题：

| 问题编号 | 问题 | 判定 |
|:---------|:-----|:-----|
| Q1 | 工具的故障是否可能引入安全相关的失效？ | 是 → `TI_Q1 = 1`；否 → `TI_Q1 = 0` |
| Q2 | 工具的故障是否可能无法检测到安全相关的失效？ | 是 → `TI_Q2 = 1`；否 → `TI_Q2 = 0` |

**TI = TI_Q1 OR TI_Q2**

| TI | 含义 |
|:---|:------|
| **TI = 0** | 工具不会或不可能引入或无法检测到安全相关的失效 |
| **TI = 1** | 工具可能引入或无法检测到安全相关的失效 |

### 3.2 各功能模块 TI 判定

#### F1 — OpenSpec 引擎

| 判定问题 | 评估 | 得分 |
|:---------|:-----|:----:|
| Q1: 故障是否可能引入安全相关的失效？ | 规范解析错误可能导致安全需求被遗漏，生成的规范数据结构错误会传递到下游所有开发环节。例如：`SHALL` 关键字被漏解析导致安全需求未生成对应代码。 | **1** |
| Q2: 故障是否可能无法检测到安全相关的失效？ | 解析失败会被立即检测（非零退出码），但**语义**错误（如错误地解析了需求的层次关系）可能不易被自动检测。不过所有 spec 输出由用户审查确认。 | **1** |
| **TI** | | **1** |

#### F2 — AI Agent 流水线

| 判定问题 | 评估 | 得分 |
|:---------|:-----|:----:|
| Q1: 故障是否可能引入安全相关的失效？ | AI 幻觉可能生成含安全缺陷的代码，或生成与安全需求矛盾的设计。LLM 非确定性输出带来不可控风险。 | **1** |
| Q2: 故障是否可能无法检测到安全相关的失效？ | 后续 CI stage (代码审查、单元测试、MISRA、SIL/HIL) 形成多层检测网络，但 AI 引入的语义级缺陷可能逃逸检测。 | **1** |
| **TI** | | **1** |

#### F3 — 代码审查

| 判定问题 | 评估 | 得分 |
|:---------|:-----|:----:|
| Q1: 故障是否可能引入安全相关的失效？ | 代码审查工具不修改代码，只产生审查意见。因此不会直接引入安全失效。 | **0** |
| Q2: 故障是否可能无法检测到安全相关的失效？ | AI 审查可能遗漏关键缺陷，但所有审查记录具有完整上下文 (diff + spec 引用)，审查意见由工程师逐条确认。 | **1** |
| **TI** | | **1** |

#### F4 — MISRA 静态分析

| 判定问题 | 评估 | 得分 |
|:---------|:-----|:----:|
| Q1: 故障是否可能引入安全相关的失效？ | 静态分析工具不修改源代码，不会引入新的安全失效。 | **0** |
| Q2: 故障是否可能无法检测到安全相关的失效？ | 已知漏报率：~29% 的 MISRA 规则 cppcheck 无法自动检测；控制流/指针别名/并发的漏报。故障可能未被检测。 | **1** |
| **TI** | | **1** |

#### F5 — CI L1 单元验证

| 判定问题 | 评估 | 得分 |
|:---------|:-----|:----:|
| Q1: 故障是否可能引入安全相关的失效？ | 单元测试框架不修改源代码，不会引入新的安全失效。 | **0** |
| Q2: 故障是否可能无法检测到安全相关的失效？ | 测试自身缺陷 (假阳性) 可能导致缺陷未检出；覆盖率门禁可能因数据损坏而误判。但退出码门禁和覆盖率门禁提供了基础保证。 | **1** |
| **TI** | | **1** |

#### F6 — CI L2 集成验证

| 判定问题 | 评估 | 得分 |

## 4. 工具错误预防与检测措施评估 (TD)

### 4.1 TD 判定方法

根据 ISO 26262-8:2018 §12.4.4，TD 判定基于工具故障被预防或检测的置信度：

| TD | 含义 | 判定条件 |
|:---|:------|:---------|
| **TD = 1** | 高置信度 — 工具故障极有可能被预防或检测 | 多重独立检测机制 + 自动验证 |
| **TD = 2** | 中置信度 — 工具故障可能被预防或检测 | 有检测机制但非完全自动或覆盖率有限 |
| **TD = 3** | 低置信度 — 工具故障极不可能被预防或检测 | 无或仅有极弱的检测机制 |

### 4.2 各功能模块 TD 判定

#### F1 — OpenSpec 引擎

| 措施类别 | 预防/检测措施 | 效果 |
|:---------|:--------------|:-----|
| **自动预防** | RFC 2119 语法校验 — 非格式输入拒绝解析 | 高 — 语法错误立即捕获 |
| **自动预防** | 需求 ID 冲突检测 — 重复 ID 报错 | 高 — 编译级检测 |
| **自动预防** | 文件大小限制 (10MB) — 拒绝过大文件 | 高 |
| **自动预防** | 需求层次结构校验 — 父/子关系合法性 | 高 |
| **自动检测** | 解析错误精确行/列定位 | 高 |
| **自动检测** | 语义差分算法 — 版本间变更检测 | 中 — 检测格式变更但非语义正确性 |
| **人工预防** | Spec 提交前人工审查工作流 | 高 — 领域专家逐条确认需求准确性 |
| **人工预防** | S.U.P.E.R 启动分析 — 每次新增需求触发 | 高 — 系统性分析新需求的完整性 |

**TD 判定理由**: OpenSpec 引擎具有完善的语法验证机制和异常捕获，所有解析失败都被阻塞。需求语义的正确性靠人工审查确认。工具错误在源头被有效检测。

| 维度 | 评估 |
|:-----|:------|
| **TD** | **1** |
| **理由** | 语法级错误被自动检测和阻塞；语义级正确性由人工审查保证；双重机制覆盖错误预防和检测 |

#### F2 — AI Agent 流水线

| 措施类别 | 预防/检测措施 | 效果 |
|:---------|:--------------|:-----|
| **自动预防** | 流水线 blocking review gate — 输出必须通过审查才能进入下 stage | 高 |
| **自动预防** | Agent 输出格式 Schema 校验 | 高 |
| **自动检测** | CI L1-L3 门禁 — 单元测试、静态分析、SIL/HIL | 高 — 功能正确性验证 |
| **自动检测** | 覆盖率门禁 — 检测测试遗漏 | 中 — C 覆盖率门禁 ≥70% |
| **自动检测** | SDD/DDD 结构完整性校验 | 中 |
| **人工预防** | Stage 切换时的人工审查 (Q&A gate) | 高 — 专家审查每个阶段输出 |
| **人工预防** | 需求 → 设计 → 代码 → 测试的双向追溯审查 | 高 |

**TD 判定理由**: AI 输出的不确定性通过多层审查和验证机制补偿 (blocking gate + CI 验证 + 人工确认)，形成有效屏障。

| 维度 | 评估 |
|:-----|:------|
| **TD** | **2** |
| **理由** | AI 输出的非确定性本质使得完全自动化预防不可行。Blocking review gate 和 CI 验证提供了较高置信度的检测，但 LLM 引入的语义级缺陷可能在某些情况下逃逸 |

#### F3 — 代码审查

| 措施类别 | 预防/检测措施 | 效果 |
|:---------|:--------------|:-----|
| **自动检测** | 4 Agent 并行审查 — 架构/领域/风格/覆盖率 | 中 — 多维度覆盖 |
| **自动检测** | 资源使用预测 (stack/heap/flash/RAM) | 中 — 预测值偏差可能 |
| **人工检测** | 每项审查记录由工程师逐条确认后合并 | 高 — 人工确认闭环 |
| **人工检测** | 二次审查 (代码 owner + 任务 owner) | 高 — 双重确认 |

**TD 判定理由**: AI 审查意见不具决策权，最终的代码合并决定由工程师做出。100% 的人工确认闭环提供了最高水平的故障检测。

| 维度 | 评估 |
|:-----|:------|
| **TD** | **1** |
| **理由** | 工具输出完全可人工复核，且强制要求人工确认后才能合并代码。AI 遗漏的缺陷由人工环节发现 |

#### F4 — MISRA 静态分析

| 措施类别 | 预防/检测措施 | 效果 |
|:---------|:--------------|:-----|
| **自动检测** | cppcheck 自动检查 ~120 条规则 | 中 — 规则覆盖 71% |
| **自动检测** | 违规结果 Schema 校验 | 高 |
| **补充检测** | AI 审查覆盖 cppcheck 无法检测的 ~49 条规则 | 中 — AI 覆盖非自动检查规则 |
| **人工检测** | Required 规则违规逐条确认 | 高 |
| **检测管理** | 偏差管理流程 — 误报/漏报正式审批 | 高 |
| **趋势监控** | 违规趋势追踪 — 异常偏离告警 | 中 |
| **回归验证** | 每次 CI 全量运行 + 测试基准对比 | 高 — 工具性能退化可被检测 |

**TD 判定理由**: 尽管 cppcheck 存在已知漏报和误报，但 AI 补充审查 + 人工确认 + 偏差管理 + 趋势监控组合形成了有效的多层检测体系。

| 维度 | 评估 |
|:-----|:------|
| **TD** | **2** |
| **理由** | 自动检查规则的覆盖率 71% 意味着 ~29% 的规则需要 AI/人工补充。AI 补充审查降低了漏报风险，但 AI 本身也可能遗漏。多层架构将 TD 提升至 2 级 |

#### F5 — CI L1 单元验证

| 措施类别 | 预防/检测措施 | 效果 |

| **TD** | **1** |

| **自动预防** | 覆盖率回归检测 — 防止迭代导致覆盖下降 | 高 |
| **自动检测** | MISRA 门禁 — 防止新增 MISRA 违规 | 高 |
| **自动检测** | 差异 diff 验证 — 确保修改范围可控 | 中 |
| **人工检测** | 每次迭代结果审查 | 中 — 取决于审查频率配置 |

**TD 判定理由**: Loop Engineering 的每次迭代都触发完整 CI 流水线验证，确保增量修改通过全量质量门禁。但由于迭代速度可能较快，人工审查可能被稀释。

| 维度 | 评估 |
|:-----|:------|
| **TD** | **2** |
| **理由** | 全量 CI 验证 (L1-L3) 提供了高强度的自动检测，但 AI 自动修改的非确定性本质和迭代速度带来的审查稀释风险，使得 TD 评定为 2 |

### 4.3 TD 判定汇总

| 功能模块 | TD | 主要检测机制 | 剩余风险 |
|:---------|:--:|:-------------|:----------|
| **F1** OpenSpec 引擎 | **1** | 语法校验 + Schema 校验 + 人工审查 | 语义级需求遗漏 (人工审查覆盖) |
| **F2** AI Agent 流水线 | **2** | Blocking gate + CI L1-L3 + 人工审查 | AI 语义级缺陷逃逸 |
| **F3** 代码审查 | **1** | 100% 人工确认闭环 | 人工遗漏 (极低，双人确认) |
| **F4** MISRA 静态分析 | **2** | AI 补充 + 人工确认 + 偏差管理 + 趋势 | ~29% 规则的 AI 补充审查遗漏 |
| **F5** CI L1 单元验证 | **1** | 退出码门禁 + 覆盖率门禁 | 测试自身缺陷 (非功能覆盖) |
| **F6** CI L2 集成验证 | **2** | 编译阻断 + SIL 断言 + HIL | QEMU/MockHAL 仿真不精确 |
| **F7** CI L2.5 HIL | **1** | 连通性检查 + 完整性校验 | 环境干扰导致的偶发性错误 |
| **F8** 证据链引擎 | **1** | 7 层校验 + SHA-256 + RSA 签名 | 几乎无 — 自动化完全覆盖 |
| **F9** 知识图谱 (TKG) | **2** | Merge Gate 一致性 + 置信度校验 | 图谱语义正确性 |
| **F10** 安全分析 | **1** | P0 gate + 独立专家评审 | 专家的个人盲点 (双人评审缓解) |
| **F13** Loop Engineering | **2** | 全量 CI 验证 + 回归检测 | AI 修改的非确定性与审查稀释 |

> **注**: F11 (SaaS Dashboard)、F12 (AI Preview)、F14 (模板市场) 的 TI = 0，不参与 TD 判定 (TCL 自动为 1)。

## 6. 置信度措施建议

### 6.1 ISO 26262-8 §12 置信度措施综述

根据 ISO 26262-8:2018 §12.4.5.2，TCL > 1 时需采取以下一类或多类措施提升使用置信度：

| 措施类别 | 编码 | 说明 |
|:---------|:-----|:------|
| **工具链冗余** | [a] | 使用不同原理的工具并行验证 |
| **人工验证** | [b] | 工具输出的人工确认 |
| **回归验证** | [c] | 工具检测能力持续验证 |
| **偏差管理** | [d] | 已知偏差的正式管理流程 |
| **测试基准** | [e] | 已知样本验证工具检测能力 |
| **确定性检查** | [f] | 验证工具输出的一致性/确定性 |
| **过程集成** | [g] | 将工具使用集成到受控流程中 |

### 7.2 关键发现

1. **无 TCL3 模块**: yuleOSH 的 14 个功能模块均未达到 TCL3，最高为 4 个 TCL2 模块。
2. **TCL2 模块均具有成熟的补偿措施**: F2/F4/F6/F9/F13 五个 TCL2 模块均设计了置信度提升措施可等效 TCL1 使用。
3. **TI=0 模块可放心使用**: F8/F11/F12/F14 四个模块的 TI=0，表示其故障不会影响安全相关的失效。
4. **核心安全关键模块均为 TCL1**: OpenSpec (F1)、代码审查 (F3)、单元验证 (F5)、HIL (F7)、安全分析 (F10) 这些直接影响安全的模块均为 TCL1。

### 8.3 评估方法论说明

本文档的评估方法遵循 ISO 26262-8:2018 §12 的要求：

1. **工具功能分解**: 将 yuleOSH 分解为 14 个功能模块进行独立评估
2. **TI 判定**: 基于每个模块是否可能引入或无法检测安全相关失效 (Q1 + Q2)
3. **TD 判定**: 基于现有的预防/检测措施的置信度 (自动 + 人工)
4. **TCL 矩阵**: TI × TD 矩阵判定 (ISO 26262-8:2018 Table 4)
5. **置信度措施**: 对 TCL2 模块提出具体措施建议

> **注意**: TI = 0 的模块 (如 F8, F11, F12, F14) 无论 TD 如何，TCL 自动为 1，无需额外置信度措施。

### 8.4 版本合规性要求

本文档适用于 yuleOSH v2.5.0。每次工具主要/次要版本变更或功能模块变更时需进行 TCL 重新评估。

| 变更场景 | 评估范围 | 处置 |
|:---------|:---------|:-----|
| 新增功能模块 | 全量评估 | 补充 TCL 文档 + 更新矩阵 |
| 现有模块功能重大变更 | 关联模块评估 | 更新 TCL 等级 |
| LLM 模型更替 | F2, F3, F10, F13 评估 | 更新 TI/TD 判定 |
| cppcheck 主版本升级 | F4 评估 | 更新 TD 判定 |
| QEMU 版本变更 | F6 评估 | 验证模拟精度变化 |
| 第三方工具更替 | 相应模块评估 | 重新判定 TI/TD/TCL |
